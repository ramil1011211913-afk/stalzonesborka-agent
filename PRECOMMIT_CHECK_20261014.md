# Проверка готовности к фиксации — 2026-10-14

## Решение

Чистая установка Python 3.12 подтверждена для CPU и GPU на этой машине. Многопроцессная эксплуатация **не прошла** из-за записи общего `last_owned.json` и несогласованного запуска/статуса обновления аукциона. Эти блокеры не скрываются успешными поисковыми запросами.

Runtime-код, зависимости и прежние 46 файлов в этом этапе не изменялись. Выполнены проверки и добавлены только инструмент проверки и этот отчёт. Ветка `experiment/beam-danger-lookahead`, HEAD `371a55c`, Git-индекс и значение Lookahead по умолчанию `0` сохранены. Коммиты, staging и переключения ветки не выполнялись.

При переносе на другую платформу нужны отдельная проверка wheels и совместимый NVIDIA-драйвер. Проверка этой машины не подтверждает произвольный CUDA/OS/Python-комплект.

## Реальный запуск и HTTP

В чистом окружении запущен настоящий Uvicorn/FastAPI. Инициализация SQLite выполнялась на отдельной копии контрольного снимка, а не на исходной базе. Для проверки журналов и сохранения собственных артефактов пути перенаправлены в новый тестовый каталог. Проверено HTTP-открытие страницы, `/api/stats`, `/api/builds` во всех трёх режимах с двумя вариантами брони и ограничениями. Последовательные и параллельные ответы совпали по сериализованным сборкам; журналы сохранены.

Проверены один CPU-процесс, два CPU-процесса и два GPU-процесса. Процессы обслуживали разные локальные порты и использовали одну тестовую базу и один каталог состояния; это позволяет воспроизводимо обратиться к каждому worker. Это не проверка балансировщика `uvicorn --workers`, контейнерного оркестратора или нескольких машин. GPU-доступность подтверждена отдельно в каждом GPU-worker.

Сеть аукциона отключена в тестовом bootstrap: свежесть задаётся управляемо, обновление заменено диагностической функцией. Реальный внешне изменяющий аукцион/сетевые квоты не затрагивались. Тестовый shutdown существует только в инструменте, не добавлен в приложение.

## Блокер 1: общий файл собственных артефактов

Запущены четыре независимых процесса с настоящим `_persist_owned_artifacts()`, по 60 записей в общий тестовый файл. Начало записи синхронизировано; внутрипроцессная блокировка в каждом worker отдельная.

| Сценарий | Успешные записи / 240 | Ошибки записи | Повреждённый JSON |
| --- | --- | --- | --- |
| Только четыре writer | 166/240 | 74 `PermissionError` (`WinError 5`) | Не обнаружен |
| Четыре writer + reader | 139/240 | 101 `PermissionError` | Не обнаружен |

Во втором сценарии выполнено 88 чтений. Итоговый файл содержит полный экземпляр записи, временных файлов не осталось. Атомарная публикация защищает от смешивания JSON, но на Windows конкурентная замена назначения между процессами может отказать. В реальном запросе это способно привести к ошибке после выполненного поиска.

Сохранение по-прежнему имеет общую семантику «последняя завершившаяся запись», без изоляции пользователя. Для нескольких workers необходим механизм координации между процессами и определение владельца состояния, например транзакционное хранение с пользовательским ключом. В этом проверочном этапе новая архитектура хранения не реализовывалась.

## Блокер 2: обновление аукциона

На двух workers с управляемо устаревшим снимком запросы поиска запустили **два независимых задания обновления**. `_refresh_state` — словарь внутри процесса: второй worker не видит владение заданием первого, `/api/refresh-status` возвращает локальное состояние.

Диагностическая функция только записывает маркер процесса и состояние; настоящая загрузка рынка и изменение исходных лотов не выполнялись. Значения прогресса в тесте содержат PID для различения workers и не являются числом загруженных артефактов. Подтверждён именно разрыв координации, а не доказана конкретная порча SQLite при реальной загрузке.

Для поддержки нескольких workers нужны общее владение заданием, общий статус и политика восстановления после падения владельца. SQLite busy timeout и блокировка отдельной записи `last_owned.json` этого не обеспечивают. До исправления нельзя рекомендовать несколько процессов приложения как готовый режим эксплуатации.

## Сохранность и следующие действия

Первоначальный перечень этого этапа содержит 2534 файла. Все прежние файлы, включая исходные данные, отчёты, пакеты просмотра и резервные копии, проверяются по SHA-256. Git-индекс также сверяется по SHA-256. Проверочные процессы остановлены; исходная база не открывалась для записи. Журналы, копии базы и venv сохранены в новом каталоге. `git diff --check` проходит.

Чистая установка пройдена. Поисковые запросы с двумя workers прошли, но многопроцессная готовность в целом **не подтверждена**. Следующий отдельный этап может устранить оба блокера, после чего потребуются повторные проверки сохранения состояния и обновления. Вариант эксплуатации с одним worker имеет проверенный объём возможностей, но не получает автоматического разрешения на стабильный выпуск или коммит.

Контрольная фиксация текущего экспериментального состояния и выпуск стабильной многопроцессной версии — разные решения. Решение о коммите остаётся отдельным явным решением пользователя. Lookahead остаётся экспериментальным и выключенным по умолчанию.
