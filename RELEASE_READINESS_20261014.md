# Подготовка к стабильному выпуску — 2026-10-14

## Результат

Подготовлены пакет сохранения незакоммиченных изменений и предварительный просмотр каждого изменённого/нового Git-файла. Проверены конкурентные поиски и настоящий браузерный путь UI → HTTP API → оптимизатор. Найденные ошибки журналирования, сохранения собственных артефактов и передачи параметров исправлены. Эвристики, целевые функции и алгоритмы поиска не менялись.

Ветка `experiment/beam-danger-lookahead`, HEAD `371a55c`, значение Lookahead по умолчанию `0`. Коммиты, переключение ветки и staging не выполнялись. Проверка Git-индекса входит в итоговый перечень сохранности.

## Конкурентные запросы

- 72 параллельных GPU-поиска: группы из трёх запросов в `balanced`, `lexicographic`, `min_budget`; Lookahead 0/1; стандартный CUDA stream и отдельные streams потоков. В 12 группах один запрос получает OOM после частичных GPU-выделений и полностью повторяется на CPU. Соседние запросы сохраняют результаты и живые GPU-массивы. Ответы совпали с соответствующими последовательными CPU/GPU-контролями. После завершения занятые блоки пула равны нулю, глобальный backend остаётся GPU.
- 18 параллельных CPU-поисков в трёх режимах при обоих флагах; полное совпадение оценок и комбинаций с последовательными контролями.
- 12 параллельных запросов настоящего `/api/builds` с тремя целями и двумя альтернативами брони на сокращённом пуле; три одновременно выполняемых запроса.
- Ещё 12 запросов `/api/builds` на полном подготовленном пуле, два одновременно выполняемых запроса, стандартная ширина 10000 и стратегия `min_budget`. Все ответы совпали по сериализованным сборкам с последовательными контрольными запросами; все журналы сохранены.

Это проверка одного процесса с несколькими потоками. Она не подтверждает безопасность нескольких процессов Uvicorn/Gunicorn, большого числа пользователей или произвольной конкурентной нагрузки. Окружение Lookahead задавалось до запуска группы и не менялось во время её выполнения.

## Найденные ошибки и исправления

**Коллизии журналов.** Старое имя JSON-журнала включало время только до секунды. В диагностическом прогоне 12 запросов создали всего шесть новых файлов. Теперь имя содержит микросекунды и UUID, открытие выполняется с режимом `x`; существующий журнал не перезаписывается. Повторная проверка сохранила 12/12 журналов. Отдельный тест проверяет 16 одновременных запросов с одинаковыми параметрами.

**Сохранение собственных экземпляров.** Прямое одновременное сохранение одного `last_owned.json` могло смешать/обрезать данные. Теперь записывается отдельный временный файл и выполняется атомарная замена. Реальный Windows-тест выявил `Access denied` при одновременной замене назначения; замена защищена блокировкой внутри процесса. 20 параллельных сохранений больших записей прошли; итоговый файл содержит одну полную запись, временные файлы очищены. Сохранение перенесено после успешной проверки поискового запроса: отклонённый запрос не заменяет сохранённое состояние.

Файл остаётся общим снимком последнего завершённого сохранения, без изоляции пользователей и без гарантии порядка начала запросов. Для нескольких процессов/пользователей нужна отдельная модель хранения; настоящую многопользовательскую эксплуатацию этот этап не объявляет готовой.

**Пользовательский интерфейс.** Раньше UI не предоставлял выбор новых целей. Теперь доступны `balanced`, `lexicographic`, `min_budget`; для лексикографического режима пользователь явно меняет порядок активных характеристик кнопками вверх/вниз. Нулевой вес удаляет характеристику из порядка, пустой порядок отклоняется локально. Это подключение уже реализованных режимов, без изменения математики.

Выбранная броня передаётся в обычный поиск, мета-поиск и прогрессию бюджета. Для последней добавлена передача профиля в каждый вызов существующего оптимизатора и HTTP 422 при неверном профиле. Кнопка обычного поиска блокирует повторный запуск до завершения, включая повторный прямой вызов обработчика. После ранних ошибок и завершения кнопка восстанавливается. Пояснена отдельная семантика ручного шаблона; направление «защита» в названиях строк соответствует пяти характеристикам заражения из текущего контракта, а не произвольному `*_accumulation`.

**Зависимости выпуска.** NumPy и Numba используются кодом, но отсутствовали в `requirements.txt`; они добавлены. `requirements-tested-cpu.txt` фиксирует непосредственные версии пакетов проверенного Python 3.12, `requirements-validation.txt` — зависимости тестов/MILP/измерений. Это не полный транзитивный lock и не доказательство установки в чистом окружении. Проверка установки из опубликованных wheels в изолированной среде остаётся отдельным условием выпуска. CuPy/CUDA сохраняют необязательный характер; их версии и системные требования нельзя считать проверенными для произвольного компьютера.

## Браузерная проверка

Использованы установленный Chrome в headless-режиме, CDP и Node без дополнительных npm/Python-библиотек. Запущен изолированный локальный HTTP-сервер с настоящим API и оптимизатором; SQLite читается только с `mode=ro&immutable=1`. Логи, сохранение собственных экземпляров и профиль Chrome находятся в новом каталоге проверки. Внешнее сохранение, обновление аукциона и исходная рабочая база не использовались.

Проверены реальные JavaScript-обработчики и отправленные запросы: баланс и все веса, бюджет и допуск, min/max, явный порядок и его перестановка, минимальная цена, смена/снятие брони, мета-поиск, прогрессия бюджета, пустая лексикографическая цель и защита от двойного запуска. Проверены корректные названия направлений оптимизации. Ответы обычного поиска отрисовываются успешно; исключений JavaScript нет. Снимки экрана сохранены.

Автоматизация использует DOM-события в настоящем браузере; это не полная проверка клавиатуры, мобильного интерфейса или доступности. Мета-поиск и прогрессия используют свои пресеты; цель и min/max обычного поиска не являются параметрами этих отдельных функций. Ручной LZ-шаблон сохраняет семантику подбора заданных артефактов.

## Безопасная стратегия фиксации

Пакет находится в `data/validation/release-readiness-20261014/`. `review-final/INDEX.md` содержит таблицу каждого изменённого/нового Git-файла, назначение, рекомендуемую группу и ссылку на отдельный patch. `review-final/manifest.json` сохраняет статус и SHA-256. `preservation-final/` содержит копии, полный tracked patch относительно HEAD и ZIP всех незакоммиченных Git-файлов, включая исключённые из будущей фиксации резервные копии. Первоначальный пакет сохранён отдельно; для просмотра и восстановления следует использовать каталоги с суффиксом `-final`.

Порядок будущей работы, без выполнения этих действий сейчас:

1. Прочитать все отдельные patches в `review/INDEX.md`, сверить контрольные суммы с рабочими файлами и итоговый отчёт. Никаких `git add -A`, `git clean`, stash, reset или checkout.
2. Согласовать точный список файлов. Runtime-модули, Builder, API/мета/Lunar, UI, обязательные зависимости и связанные тесты образуют одну согласованную группу: делить их по отдельным старым этапам без проверки промежуточных состояний рискованно.
3. При явном разрешении на staging добавить только пути из согласованного списка. Просмотреть `git diff --cached --check` и `git diff --cached`, убедиться, что туда не попали данные, секреты, резервные копии и диагностические дампы.
4. Повторить необходимые проверки именно подготовленного состояния. Только после отдельного явного разрешения создавать коммит. Вариант с отдельной последующей фиксацией инструментов/отчётов допустим; runtime и тесты должны оставаться согласованными.

Резервные копии `app/*.backup-*`, старый вспомогательный `app/exact_validator.py` и `exact_validator_*.txt` сохраняются в пакете, но по умолчанию не предлагаются к фиксации. Это исключение из списка staging, а не удаление файлов. Данные и `.env` не входят в Git-пакет; проверяется их сохранность, содержимое секретов не выводится.
