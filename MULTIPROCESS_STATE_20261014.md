## Собственные артефакты

`app/_app_state.py` создаёт отдельную `Config.DATA_DIR/app_state.sqlite3`, WAL, `busy_timeout=30000`, короткие соединения с явным закрытием. Запись списка выполняется транзакцией `BEGIN IMMEDIATE`; ревизия увеличивается в той же транзакции. Последняя завершённая запись становится общей текущей записью. Никакой замены JSON-файла через Windows filesystem теперь нет.

`GET /api/owned-artifacts` возвращает `scope`, список `artifacts` и `revision`. Если запись отсутствует, существующий `last_owned.json` импортируется один раз; вставка не заменяет уже сохранённое состояние. Оригинал не удаляется и не перезаписывается. Пустой явно переданный `owned=[]` очищает SQLite-состояние и не допускает повторного восстановления старого JSON. Отсутствующий параметр не изменяет сохранённый список. Поиск по-прежнему использует собственные артефакты из текущего запроса, без молчаливого добавления сохранённого списка.

Сохраняются все переданные поля записей, включая идентификаторы экземпляров. Сохранение остаётся после принятого поискового запроса; отклонённый запрос не заменяет состояние. JSON должен содержать список записей и конечные значения. Ошибка чтения/структуры импортируемого JSON возвращается явно, без изменения оригинала.

## Владение обновлением

Одна SQLite-запись на регион хранит токен владельца, поколение задания, срок lease, прогресс, ошибку и PID. Захват выполняется транзакцией. Активный lease не позволяет другому worker или CLI-коллектору запустить второе обновление. Повторный запуск после завершения, ошибки или истечения lease получает новое поколение.

Обычный lease — **60 секунд**, heartbeat — каждые 20 секунд. Истёкшее владение не продлевается. Следующий запрос поиска автоматически восстанавливает истёкшее задание, даже если частично обновлённые данные уже выглядят свежими по `MAX(collected_at)`; возможен также явный `POST /api/refresh-auction`. Без запросов постоянный супервизор не запускается. Статус `/api/refresh-status` читается из общего хранилища.

Токен и поколение проверяются при heartbeat, прогрессе, завершении и перед публикацией лотов. Устаревший worker не может стереть статус нового задания, продлить прежнее владение или записать результаты. Публичный статус не раскрывает токен.

`app/database.py:replace_lots_for_item()` атомарно заменяет все лоты одного артефакта в одной market-транзакции. Во время её выполнения удерживается SQLite writer lock хранилища состояния: новое поколение не может быть захвачено до завершения market commit. Соединения закрываются; ошибка откатывает всю замену. `app/collector.py` использует этот путь для API и CLI. Ошибки получения лотов оставляют старые лоты соответствующего артефакта и публикуются как общее неуспешное завершение, а не как ложный успех.

Это атомарность **одного артефакта**, не публикация всего аукциона единым снимком. Прогресс хранится отдельно от market commit: после падения он может отставать, но старый владелец не может продолжить публикацию. Сетевые запросы, уже находящиеся в полёте, не отменяются мгновенно; безопасность обеспечивается fencing перед записью. Прямые внешние записи в market DB в обход коллектора не входят в протокол.

Добавлены девять поведенческих тестов: импорт/очистка без восстановления старого JSON, ревизии и пространства владельцев, единственный claim, fencing старого владельца, атомарный rollback market-замены, heartbeat, общий статус коллектора, API и освобождение lease при ошибке запуска потока. Обнаруженная гонка первого переключения SQLite в WAL устранена ограниченным повтором только lock-ошибок.

## Границы готовности

Проверенные межпроцессные блокеры устранены для общей сессии на одной Windows-машине с общим локальным SQLite. До запуска следует остановить все workers старой версии: совместную работу старого JSON writer и нового SQLite-хранилища нельзя считать согласованной миграцией. Исходный JSON сохраняется для проверки и возврата к прежнему состоянию.

Ни эти проверки, ни прежние MILP-сопоставления не дают гарантии глобального оптимума Beam или актуальности предложения после изменения рынка. Более разнообразные рыночные снимки, длительная нагрузка и пользовательская изоляция остаются отдельными задачами. Решение о контрольном коммите и о стабильном выпуске остаётся отдельным решением пользователя; Lookahead не включён по умолчанию.
