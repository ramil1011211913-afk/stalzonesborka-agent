# Экспериментальный портфельный поиск — 2026-10-14

Реализован отдельный явно вызываемый режим. Поведение обычного `build_artifact_sets()` сохраняется; Lookahead по умолчанию остаётся выключенным. Контрольная точка — `c785e231b91b28dd0214cc1b72cf2debbbfcdbe3`, ветка `experiment/beam-danger-lookahead`. Новые изменения не закоммичены и не добавлены в индекс.

## Реализация и вызов

Новый модуль `app/_portfolio_search.py` предоставляет:

```python
from app._portfolio_search import build_portfolio_sets

result = build_portfolio_sets(
    budget=11_880_000,
    container_id="dkln",
    priorities={"speed_modifier": 10},
    allow_duplicates=True,
    max_attempts=3,
)
builds = result.builds
attempts = result.attempts
```

Запрос принимает остальные обычные параметры построения: ограничения, собственные экземпляры, повторы, броню, режим оптимизации, порядок и допуск lexicographic, фиксированные масштабы. Возвращается `PortfolioResult`: сборки, диагностика попыток, установленный лимит и общее время. Подключения к UI, HTTP API и метаоптимизатору на этом этапе нет. Для следующего экспериментального запроса, включая замену брони, нужно снова явно вызвать `build_portfolio_sets`; существующие механизмы обычного повторного поиска не менялись.

| Порядок | Стратегия | Beam Width | Lookahead |
| --- | --- | --- | --- |
| 1 | fast | 2000 | 0 |
| 2 | quality | 2000 | 1 |
| 3 | wide_control | 10000 | 1 |

`max_attempts` — целое число от 1 до 3; выполняется соответствующий префикс расписания. **Лимит действует на каждый подготовленный набор «контейнер + броня»**, а не на суммарное число вызовов движка запроса. Например, один контейнер и две брони при лимите 3 дают 6 вызовов Beam. Автоматической остановки по плато или обещания жёсткого лимита времени нет. Невыполнимый запрос не включает скрытый дополнительный повтор с шириной 50000.

Подготовка артефактов, собственных экземпляров, контейнеров/брони и Objective происходит один раз в builder. Во всех попытках одного набора используются те же кандидаты; все наборы запроса используют один объект Objective и общие масштабы. Нативный Beam получил необязательный явно задаваемый `danger_lookahead`; при отсутствии аргумента сохранён прежний выбор по окружению. Переменные окружения и глобальный backend портфель не меняет.

Builder получил приватный `_beam_search_fn` для отдельного эксперимента. Без него выбор движка и существующие ширины полностью сохраняются. С ним маленькие наборы также проходят Beam, что позволяет сравнивать портфель с независимым перебором.

Уникальные комбинации всех попыток объединяются до общей финальной проверки и разнообразия. Их итоговые игровые значения, допустимость и ранг пересчитываются; учитываются бюджет, физическая доступность, ограничения характеристик, заражение и число компенсаторов. Balanced сравнивается по общей оценке и цене, lexicographic — по общим квантованным приоритетам и цене, min_budget — по цене. Результат ранней успешной попытки сохраняется даже при ухудшении или отсутствии результатов следующей. Ошибки алгоритма не скрываются; существующий CUDA OOM fallback повторяет каждую отдельную попытку на CPU с теми же параметрами.

В min_budget существующая логика движка намеренно не использует danger Lookahead. Поэтому первые две конфигурации здесь имеют одинаковую ширину и фактически одинаковую стратегию минимизации цены; лишняя попытка пока сохранена для точного соответствия экспериментальному расписанию.

Цена как разрешение равенств проверена отдельными тестами и сравнением попыток; совпадение основной MILP-цели не следует трактовать как самостоятельный сертификат минимальной цены среди всех её равнозначных решений.

Independent oracle выполнен на 8 случайных маленьких наборах с физическими альтернативами, двумя профилями брони, нелинейной stopping protection, заражением, бюджетом и всеми режимами. Завершены 144 контрольных запуска: 96 портфельных CPU/GPU и 48 Numba как контроль прежнего движка; в каждом проверены два профиля брони, всего 288 профильных проверок. Расхождений нет. Флаг окружения 0/1 в этих запусках не меняет расписание портфеля.

## Задержки и память

Измерены 20 конфигураций: GPU/CPU, без брони/две брони, обычный поиск/три отдельные стратегии/портфель. Для каждой — прогрев и три измеренных запроса, всего 60 измеренных запросов. CPU-измерения выполнены на проверенном Python 3.12 с принудительным CPU backend. Ниже сценарий движения с двумя вариантами брони; ordinary — прежний поиск с шириной 10000 и Lookahead=0.

Память сэмплировалась каждые 10 мс, поэтому это измеренные пики, а не строгие максимумы. p95 по трём повторам — предварительная описательная оценка, не надёжная характеристика длительной нагрузки. CuPy used относится к занятым блокам этого процесса; полная VRAM, кеш и чужие процессы — отдельные величины.

**Вывод:** портфель работает корректно на проверенных задачах, но на этом снимке не улучшает результат относительно узкого Lookahead. Широкая контрольная попытка существенно увеличивает время и пиковую память. Оставляем портфель отдельным экспериментом; не включаем его или Lookahead автоматически. Следующая содержательная проверка — новые наборы, на которых quality отличается от wide_control, либо исследование ранжирования/блочного расширения. Плато, согласие трёх стратегий и 22/22 MILP не доказывают глобальный оптимум на произвольном аукционе.
