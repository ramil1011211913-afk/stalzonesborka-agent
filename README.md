# Stalzone Artifact Build Optimizer

Оптимизатор сборок артефактов для STALCRAFT / Stalzone (регион EU).
Подбирает 4–7 артефактов под бюджет, контейнер, броню, приоритеты и пороги статов,
считает носибельность, EHP и лечение, умеет экспортировать сборки в lunar-zone.

## Стек

- Python 3.12, FastAPI, Uvicorn
- SQLite (WAL), NumPy, Numba, SciPy/HiGHS
- Один HTML-файл интерфейса: `app/templates/index.html`

## Быстрый старт

```bat
start.bat
```

Скрипт сам переходит в свою папку, проверяет Python 3.12 и зависимости,
инициализирует БД и поднимает сервер на <http://127.0.0.1:8123>.

Ручной запуск:

```bat
py -3.12 -m uvicorn app.main:app --host 127.0.0.1 --port 8123
```

Ключи Stalzone eAPI задаются в `.env` (см. `.env.example`). Поддерживаются
несколько пар ключей `STALCRAFT_CLIENT_ID_N` / `STALCRAFT_CLIENT_SECRET_N`
для параллельного сбора аукциона.

## Данные

- `data/stalzone.db` — артефакты, контейнеры, броня, активные лоты и история продаж.
- Обновление аукциона: `POST /api/refresh-auction`, прогресс — `GET /api/refresh-status`.
- Тот же сбор идёт автоматически в фоне, если данные старше 6 часов.
- Вместе с активными лотами собирается история продаж (`/api/price-history`).
  Повторный сбор не создаёт дублей; на предмет хранится окно до 500 записей
  (по умолчанию запрашиваются 200 последних).
- Пагинация лотов проверяется на полноту: изменение `total`, обрыв страницы или
  превышение лимита отклоняют предмет, а не публикуют неполный рынок. Ошибка eAPI
  не стирает уже сохранённые лоты предмета.
- CLI: `py -3.12 -m app.collector --auction` (добавьте `--no-history`, чтобы пропустить историю).

## Приоритеты и процент неизвестных лотов

- Приоритеты задаются по статам артефактов, пороги — по итоговым статам сборки.
- «Общая скорость» (`total_speed`) — производная метрика:
  `speed_modifier + sprint_speed_modifier`. Она материализуется в статах
  артефактов, бонусах контейнера/брони и во всех поисковых движках, поэтому
  приоритеты, пороги, MILP и UI используют одно и то же значение.
- Для неизвестного процента доступны три точки расчёта:
  - `minimum` («Гарант. минимум») — минимум тира. Строгая нижняя оценка для
    выбора; это не гарантия характеристик и носимости при всех возможных роллах.
  - `midpoint` («Ожидаемо») — середина тира. Ожидаемая оценка при равномерном
    скрытом ролле; **выбрана по умолчанию в UI** как лучший практический
    компромисс между ценой и риском.
  - `maximum` («Максимум тира») — максимум тира. Оптимистичный потолок;
    историческое поведение API по умолчанию.
- У лотов и owned-экземпляров с сохранённым процентом он сохраняется как есть
  во всех трёх режимах: например, Сетчатка rare +15 с 140.14% остаётся 140.14%,
  а не превращается в 130%.
- Процент считается известным только при реальном `stats_random` от eAPI.
  Если API его не вернул, коллектор пишет максимум тира как значение для
  обычного расчёта; режимы распознают такой максимум как неизвестный и берут
  выбранную точку тира. Это касается и неисследованных лотов (`ptn=0`).
- Известность процента хранится в `ArtifactOption.art_percent_known`; загрузчики
  выставляют её явно, а не по умолчанию.
- API: `unknown_percent=minimum|midpoint|maximum`. `conservative=1` оставлен
  для обратной совместимости и означает `minimum`; явно переданный
  `unknown_percent` важнее `conservative`. Экспорт в Lunar-zone принимает тот же
  параметр, чтобы выгрузка совпадала с поиском.
- Почему по умолчанию `midpoint`: известный низкий ролл (например, 117.02% при
  диапазоне 115–130%) часто дороже неизвестного лота, а середина даёт выигрыш в
  ожидании при ограниченном худшем случае. По 228 известным роллам в базе
  среднее `stats_random` ≈ 0.16, то есть скрытый ролл близок к середине.
  `tests/test_unknown_percent_modes.py` проверяет все три режима, сохранение
  известного процента и выбор лота на паре Гелий q2/+15.
- `roll_optimize=1` (UI: «🎲 Планировать роллы») включает планирование точных
  целевых роллов для неизвестных процентов. Для `midpoint` и `maximum` поиск
  стартует от максимума тира, а затем для фиксированного набора артефактов решает
  небольшую целочисленную задачу в сотых процента: например, два Браслета q2/+15
  при 130% не проходят по пси-накоплению, а пара `130.00%` + `120.47%` проходит.
  Если набор уже проходит на максимуме тира, роллы остаются на максимуме:
  tie-break не понижает контр-артефакт только ради заполнения запаса.
- `unknown_percent=minimum` (включая `conservative=1`) — это гарантия, поэтому
  при включённом планировании роллов поиск и проверка остаются на минимуме тира.
  План может предложить целевые роллы выше минимума, но показанная сборка,
  проценты и статистика остаются минимальными; план лишь цель, а не замена
  гарантии. Если план невозможен, минимум-сборка сохраняется. Так гарант-минимум
  продолжает собираться, а планирование роллов не выдаёт максимум за минимум.
- Известные проценты и owned-экземпляры не меняются; план является целью для
  неизвестных лотов, а не гарантией покупки. Режим несовместим с `min_budget` и
  `guaranteed_carryable`. С Max Quality планирование совместимо: для
  `midpoint`/`maximum` MILP выбирает победителя по максимуму тира, затем для его
  фиксированного набора подбираются роллы; если роллы меняются, доказательство
  оптимальности больше не заявляется и статус понижается до `FEASIBLE`. Для
  `minimum` MILP выбирает и доказывает победителя на минимуме, а план остаётся
  информационным и не понижает доказательство. Если план невозможен,
  показывается исходная сборка с причиной в `roll_plan`. Нелинейные цели
  (EHP/HPS) и `stopping_protection` отклоняются, а не приближаются. План и его
  статус возвращаются в `roll_plan` каждой сборки и в `roll_plan_search` ответа
  API.

## Важно про документацию

Актуальная математика и пороги — в коде (`app/builder.py`, `app/_numba_search.py`,
`app/_survivability*.py`), а не в старых промптах. В `SYSTEM_PROMPT.md` и
`REBOOT_PROMPT.md` сохранились устаревшие значения (например, старые пороги
носибельности и защита frost контейнером). Корневые `*_202610*.md` — это журнал
quality-gate проверок, а не описание текущего состояния.

## Статус подсистем

- Основной поиск: Beam (большие пулы) и Numba C(n,k) (малые пулы); глобальный
  оптимум не гарантируется. Для lexicographic-режима и пороговых задач включены
  проверенные доводчики incumbent и многопроходный Beam. Контрольный gate на
  замороженном рынке (20 сценариев): 10 улучшений, 10 равенств, 0 регрессий.
- `max_quality` (MILP, HiGHS): включается файлом `app/_max_quality_release.json`;
  статус `OPTIMAL` относится только к подготовленному пулу.
- Survivability: production-код соответствует V2.6. Более поздняя V3.0 лежит в
  `data/validation/` со статусом research-only / NO-GO и в рабочее дерево не перенесена.
