# Полный повтор Beam Search на CPU при CUDA OOM — 14.10.2026

Ветка `experiment/beam-danger-lookahead`, HEAD `371a55c` сохранены. Коммитов и переключений веток нет. Lookahead по умолчанию остаётся `0`. Целевая функция, ограничения, физические идентичности и эвристики поиска не изменялись.

## Реализация

Публичный `search()` теперь управляет попытками. `_search_impl()` выполняет один полный поиск с явно заданным локальным backend. Сохранены прежняя сигнатура публичного метода, формат результата и предварительный выбор CPU для ширины луча более 20 000.

При подтверждённом OOM:

1. Неудачная GPU-попытка полностью прерывается.
2. Из traceback, включая цепочки `__cause__`/`__context__`, удаляются ссылки на завершившиеся кадры. Иначе кадры удерживали бы временные массивы и мешали освобождению памяти.
3. После выхода из блока обработки исключения собираются оставшиеся циклические ссылки, синхронизируется текущий CUDA stream и освобождаются свободные блоки его GPU-пула и pinned-memory пула.
4. Весь поиск повторяется с исходными аргументами и NumPy, начиная с построения матриц и уровня 0. Ширина луча и ограничения не уменьшаются; частичный GPU-луч не переносится.

Один неизменяемый объект `Objective` и значение флага Lookahead фиксируются до первой попытки и используются в повторе. `_GPU_OK` не переключается: следующий или параллельный запрос сохраняет обычный выбор backend. Сброс CUDA device не выполняется.

Распознаются только:

- `cupy.cuda.memory.OutOfMemoryError`;
- `CUDARuntimeError` со статусом 2 (`cudaErrorMemoryAllocation`);
- `CUDADriverError` со статусом 2 (`CUDA_ERROR_OUT_OF_MEMORY`).

Текст сообщения не используется для распознавания OOM. Обычный `MemoryError` хоста, ошибки формы массивов, CUDA illegal address и другие исключения проходят наружу без повторного поиска. Ошибка CPU-повтора также проходит наружу; рекурсивного fallback нет. При очистке допускается только повторный подтверждённый OOM, который отдельно логируется; другая ошибка очистки прерывает выполнение и не скрывается.

GPU-пул освобождает свободные блоки, сохраняя активные выделения; для разделённых блоков есть ограничения освобождения. Это соответствует [документации CuPy MemoryPool](https://docs.cupy.dev/en/v14.2.0/reference/generated/cupy.cuda.MemoryPool.html). Коды ошибок проверены по [CUDA Runtime API](https://docs.nvidia.com/cuda/archive/8.0/cuda-runtime-api/group__CUDART__TYPES.html) и [CUDA Driver API](https://docs.nvidia.com/cuda/archive/12.6.0/cuda-driver-api/group__CUDA__TYPES.html).

Попутно исправлен выбор backend при выдаче результата: CPU-поиск больше не вызывает `cp.asnumpy` только из-за доступности GPU. В производственных вызовах `_score_vec` backend передаётся явно, поэтому CPU-повтор не выполняет скрытых CuPy-операций.

## Точки выделения памяти

Обработчик охватывает всю попытку, включая вспомогательные методы. GPU-память может выделяться в следующих местах:

| Участок | Основные массивы и временные буферы |
|---|---|
| Начальный перенос | Матрица характеристик, цены, счётчики, группы физических конфликтов, индексы, ограничения, коэффициенты и текущий луч |
| Lookahead | Таблица бюджетной компенсации, бюджетные границы, индексация и временные массивы поиска границы бюджета |
| `min_budget` | Нижние/верхние суффиксные оценки и таблица нижней стоимости продолжения |
| Обычное расширение | Маски порядка, бюджета, количества компенсаторов и конфликтов; `where`, индексы пар, временные ключи и сортировка |
| Оценка вариантов | Матрицы новых характеристик, итоговые преобразования, заражение, дефициты ограничений, оценки и лексикографические ранги |
| Отбор луча | `argpartition`, индексы равных оценок, маски конечности, ключи `lexsort`, выбранные массивы нового луча |
| Блочный `min_budget` | Временные массивы блока, объединение лучших блоков и повторный отбор; существующий предел блока 262 144 сохранён |
| Завершение | Итоговые характеристики, маски допустимости, фильтрованные массивы, сортировка и перенос результата в NumPy |

Начальные вычисления уровня 0 и построение исходных таблиц выполняются на CPU, затем необходимые массивы переносятся на GPU. Их состояние также заново строится после OOM. Исходная проверка доступности CUDA при импорте модуля сохранена.

## Проверки

Полные наборы:

| Окружение | Lookahead | Результат |
|---|---:|---|
| Python 3.12 / CuPy 14.2.0 / CUDA | 0 | **243 пройдено** |
| Python 3.12 / CuPy 14.2.0 / CUDA | 1 | **243 пройдено** |
| Python 3.15 / CPU | 0 | **217 пройдено, 26 пропущено** |

Пропуски CPU: 23 проверки требуют CUDA, одна — FastAPI, две — SciPy. Два предупреждения GPU-набора относятся к TestClient/AnyIO. После уточнения очистки цепочек исключений повторно прошли все 63 проверки OOM на GPU-окружении и 61 на CPU; две проверки реальной CUDA на CPU пропущены.

Добавлены 63 проверки:

- OOM на `asarray`, `where`, `lexsort`, `asnumpy` для трёх режимов, обоих значений Lookahead и обоих правил повторов;
- сравнение результата с полным CPU-поиском и проверка передачи исходных аргументов, идентичности `Objective`, бюджета, ограничений и физических ID;
- отказ от fallback для произвольных исключений и `MemoryError` хоста;
- распознавание только подтверждённых типов OOM и кодов Runtime/Driver;
- освобождение ссылок из traceback и цепочки причин до очистки, передача ошибки CPU наружу;
- фиксация флага Lookahead при изменении окружения между попытками;
- чистый CPU-путь при предварительном выборе ширины более 20 000;
- обработка ошибок очистки без скрытия других CUDA-ошибок;
- реальный OOM через ограничение стандартного пула CuPy: чужой живой массив сохраняется, временные выделения поиска не остаются занятыми, результат совпадает с CPU;
- искусственный OOM после нескольких реальных GPU-переносов: все созданные временные массивы уничтожаются до CPU-повтора.

Ограничение пула в тесте восстанавливается в `finally`. Память устройства целиком не исчерпывалась. Существующие проверки независимого полного перебора продолжают сопоставлять CPU/CUDA по итоговым характеристикам, ограничениям и целевой функции на маленьких задачах.

## Контрольный снимок и время

Все 11 регрессионных сценариев обычного поиска повторены по три раза при обоих значениях Lookahead. Нарушений проверяемых ограничений нет, контрольные показатели сохранились:

- balanced, бег 10 / здоровье 8: **11,448936% / +0,887250%**;
- движение с Lookahead: **18,498386%**;
- пулестойкость с Lookahead: **150,082576**;
- остановка: **66,502794**;
- `min_budget`, бег ≥10%: **1 853 444**.

Дополнительно выполнены отдельные последовательные замеры `balanced`, `lexicographic` и `min_budget`: обычный GPU-поиск, прямой CPU-поиск и принудительный OOM на первом GPU-переносе с последующим CPU-повтором. Для каждого сочетания режима и флага — три повторения. В журнале каждого OOM-вызова ровно две попытки: `gpu`, `cpu`.

Медиана полной сборки, секунды:

| Режим | Lookahead | GPU | CPU | OOM → CPU |
|---|---:|---:|---:|---:|
| balanced | 0 | 0,536 | 5,552 | 5,268 |
| balanced | 1 | 0,578 | 6,387 | 6,765 |
| lexicographic | 0 | 0,667 | 10,127 | 10,050 |
| lexicographic | 1 | 0,872 | 10,557 | 10,654 |
| min_budget | 0 | 1,415 | 6,970 | 7,040 |
| min_budget | 1 | 1,445 | 7,415 | 7,391 |

Ширина луча для первых двух режимов — 10 000, для `min_budget` — 20 000 согласно существующей стратегии builder. Lookahead внутри `min_budget` по-прежнему отключён.

Во всех шести сочетаниях CPU и OOM-повтор вернули полностью одинаковые сериализованные сборки. Лучшие характеристики и цены CPU/GPU совпали. В лексикографическом режиме без Lookahead сохраняется прежнее эвристическое отставание по бегу: 12,016612% против 12,298386% с Lookahead. Ошибка памяти не меняет семантику цели и не исправляет ограниченность конечного луча.

Различия CPU и OOM-медиан включают шум короткого локального замера; отрицательная разница не означает ускорения от OOM. Очистка и повтор первой стадии дают дополнительную работу, но основная стоимость — полный CPU-поиск. Для OOM на позднем уровне к CPU-времени добавится уже потраченное GPU-время. Контроль пиков RAM/VRAM и длительный стресс-тест не выполнялись на этом этапе.

MILP-модели на этом этапе не пересчитывались: целевая функция и допустимость не изменены. Сертификаты предыдущего этапа сохранены. CPU-повтор может завершиться собственной ошибкой памяти или другой ошибкой; такие ошибки передаются вызывающему коду.
